The five taxes you pay when prompts live in source code — and how the library pays them for you.

Every tweak is a deploy

Change one word in a prompt and you're in a PR, CI, and a ship window. So people stop iterating — or worse, they hot-patch prod.

edit a version, get a review, publish with one call — rollback too

You find regressions from users

"The bot got dumber last week." Which change did it? Nobody knows; there's no score attached to any prompt version.

an LLM judge scores every candidate; a regression blocks the publish automatically

Anyone can change anything

Prompt edits skip review trails entirely. A whole personality swap can ship with one string diff nobody reads.

draft → review → approved → live, enforced by the database itself

Prompts scattered everywhere

Strings in ten files across three repos. No way to search them, no idea which agent uses which version.

one library, hybrid meaning + keyword search, a git mirror export when you want PRs

It broke in prod and nobody noticed

Latency doubled, guardrails started firing, the eval score slipped — three days before anyone looked at a dashboard.

alert rules evaluate the instant data lands; fired alerts stream to you live

You could stitch this together

The usual answer is a stack of prompt tooling — another service to run, another schema to sync, another bill. This is one database you already know how to operate.

An LLM observability platform

Langfuse, LangSmith, PromptLayer and friends give you tracing and evals — as a separate service. New deploy target, per-seat pricing, and your prompts living in someone else's store.

documents + change streams in the MongoDB you already run

Prompt files in the repo

YAML or Python constants: versioned by git, sure — but no eval gate, no A/B routing, no rollback without a deploy, and no live view of what's actually serving.

lifecycle, evals, and routing as database behavior — with a git mirror when you want diffs

Feature flags + a dashboard

Flags can flip a prompt on and off, but they can't score it, review it, or tell you which version produced a bad answer. The dashboard tells you that something happened, hours later.

every run recorded with version, variant, tenant, tokens — and alerts on the write

Everything is a document

No new services, no schemas to sync, no cron jobs. The same store that serves your prompts governs them, evaluates them, and watches them. Take the tour to see each piece live →

Version control with a review trail

Draft → review → approved → active, enforced by the database itself. Publishing flips versions inside a transaction; rollback is one call. Every version carries who submitted, approved, and shipped it.

$jsonSchema lifecycle + transactions

The eval gate

Golden cases run through a candidate prompt and scored by an LLM judge. A regression against the baseline blocks the publish — on the record, with both scores named.

LLM-as-judge, scores as documents

Hybrid retrieval

Ask in plain language: Vector Search ranks by meaning, Atlas Search by words, one server-side stage fuses them. Every hit shows which retriever contributed what.

$rankFusion + autoEmbed vectors

Tools + guardrails, served as config

The resolve endpoint returns the full agent bundle: prompt, callable tools with JSON-Schema args, and active guardrails — injection refusal, mid-stream phrase cuts, token caps. All enforced server-side.

one resolve, the whole runner config

Alerting on the write

Rules are documents. The moment a run or eval lands, rules evaluate; fired alerts stream to every open console tab over the change feed. Latency spikes, guardrail spikes, score drops — zero polling.

change streams as the alert bus

A git mirror when you want PRs

One command flattens the library into frontmatter'd Markdown — a version tree your team can diff, blame, and review in any git workflow. The database stays the source of truth.

bun run export
